1. Ringkasan Implementasi

Project Modul 5 dikembangkan dengan RBAC berbasis tabel roles, permissions, dan role_permissions. Permission dimuat sekali saat startup ke PermissionSet. Keputusan yang tidak membutuhkan data dipasang pada route melalui RequirePermission, sedangkan keputusan berdasarkan ownership dilakukan di service.

Entity student memperoleh owner_id. Nilainya selalu diambil dari user pada access token ketika POST dan tidak tersedia di request struct, sehingga klien tidak dapat mengaku sebagai pemilik lain melalui mass assignment.

    if current.UserID == ownerID { return true }
    return perms.Can(current.Role, anyPermission)
}

5. Analisis

5.1 Mengapa ownership tidak dipindahkan ke middleware?

Pada implementasi ini, RequirePermission hanya menerima identitas dari JWT dan nama permission. Untuk mengetahui pemilik student, kode harus memanggil StudentRepository.FindByID dan membaca OwnerID. Karena repository digunakan oleh StudentService, pemeriksaan GET/PUT/PATCH ditempatkan di service agar middleware tidak bergantung pada database maupun struktur entity.

5.2 Risiko pemeriksaan terbagi di route dan service

Risiko konkretnya adalah endpoint baru dapat lupa diberi penjaga, khususnya route ownership yang terlihat tidak memakai RequirePermission. Risiko dikurangi dengan menempatkan seluruh mapping endpoint dalam route/route.go, memakai pola konsisten, dan menguji pure function authorization secara terpisah. Pengujian matriks endpoint tetap diperlukan untuk memastikan tidak ada jalur yang terlewat.

5.3 Kasus dosen wali dan mahasiswa bimbingan

RBAC saja tidak memadai karena keputusan bergantung pada relasi antara dosen dan mahasiswa tertentu, bukan hanya nama role. Sistem perlu menambahkan atribut/relasi bimbingan di database dan aturan ABAC di service, misalnya mengizinkan akses bila student.advisor_id == current.UserID, di samping permission RBAC yang sudah ada.
